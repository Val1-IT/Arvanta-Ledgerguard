# LedgerGuard v0.3 — Adapter SDK + Odoo

**First slice implemented on `feat/v0.3-odoo-adapter` — not a general Odoo product.**

Status: planning document plus a bounded `@ledgerguard/odoo` inventory-adjustment adapter. Do not treat this as broad ERP support.

---

## 1. Problem statement

v0.2 proved DETECT → AUTHORIZE → EXECUTE → VERIFY on a **synthetic PostgreSQL ledger** that LedgerGuard owns. That is not proof that LedgerGuard is an execution-integrity runtime for AI agents on **external systems of record**.

An external developer should be able to say:

> An AI agent can propose an action. LedgerGuard authorizes it, executes it only through a constrained adapter, and independently verifies that the system-of-record state satisfies the approved invariants.

v0.3 must prove that sentence against **Odoo**, using Odoo business primitives, not LedgerGuard’s demo tables.

## 2. Why an Adapter SDK is necessary

Today `@ledgerguard/core` already has `SystemOfRecordAdapter` / `SystemOfRecordSession`. That port is useful but **demo-schema shaped**:

- `loadInvestigationInput()` returns `InvestigationInput` (`products`, `inventory_movements`, `inventory_valuation`, …)
- `applyCorrection()` takes `ProposedCorrection` with SQL-ish `table` / `field` / `beforeValue` / `afterValue`
- PostgreSQL implements this by allowlisted `UPDATE`

An Odoo adapter that fakes those tables by writing Odoo SQL would be a lie. The SDK must express **actions and state snapshots** that adapters can project from their own primitives, without requiring a PostgreSQL schema.

The runtime (policy, approval, idempotency, receipts, recovery classification) stays in LedgerGuard. The adapter never becomes the authority.

## 3. Current PostgreSQL coupling

| Coupling | Where | v0.3 implication |
| --- | --- | --- |
| Demo ERP tables | `packages/postgres`, `src/db/schema.ts` | Stay as the **reference adapter**, not the domain model |
| `InvestigationInput` | `@ledgerguard/core` types | Keep for v0.2 detectors; Odoo must supply a **projected snapshot** or a new snapshot type |
| `ProposedCorrection.table` | core + postgres allowlist | Odoo must use **typed actions**, not table names |
| `PostgresExecutionKeyStore` | app `execute.ts` | Keys/journal may remain in LedgerGuard’s DB even when the SoR is Odoo |
| `idempotencyInNativeTransaction` | postgres adapter | Odoo typically **cannot** join LedgerGuard’s DB transaction |
| `beforeCommit` plan transitions | `src/remediation/execute.ts` | PostgreSQL-only; Odoo uses the v0.2 recovery protocol |

Do not rip out the PostgreSQL adapter. It remains the strongest transactional implementation and the test oracle for the SDK contract.

## 4. Proposed interfaces

Evolve the existing port rather than inventing a parallel runtime. Suggested additions (names may change during implementation):

```ts
interface AdapterCapabilities {
  nativeTransactions: boolean;
  idempotencyInNativeTransaction: boolean;
  supportsCompensation: boolean;
  supportsSimulation: boolean;
  supportsStateVersioning: boolean;
}

interface SystemOfRecordMeta {
  systemId: string;
  systemType: string;       // 'postgres' | 'odoo' | ...
  adapterVersion: string;
  capabilities: AdapterCapabilities;
}

interface StateFingerprint {
  algorithm: 'sha256';
  value: string;
  records: Array<{ type: string; id: string; version?: string }>;
}

interface AdapterSession {
  loadRelevantState(scope: ExecutionScope): Promise<ProjectedSnapshot>;
  fingerprint(scope: ExecutionScope): Promise<StateFingerprint>;
  validateAction(action: ConstrainedAction): Promise<ValidationResult>;
  simulate?(action: ConstrainedAction): Promise<SimulationPreview>;
  executeAction(action: ConstrainedAction): Promise<ActionResult>;
  verifyPostconditions(expected: VerificationExpectation[]): Promise<VerificationResult>;
  classifyRecovery?(approved: ConstrainedAction[]): Promise<'applied' | 'not_applied' | 'ambiguous'>;
  compensate?(action: ConstrainedAction): Promise<CompensationResult>;
}
```

`runInTransaction` remains **optional in spirit**: adapters with native transactions implement it; Odoo implements a **unit-of-work** that may be a single RPC call or a documented multi-call sequence plus recovery.

v0.2 `SystemOfRecordAdapter.runInTransaction` can stay as the PostgreSQL path. The SDK should wrap it as `capabilities.nativeTransactions === true`.

## 5. Adapter capability model

| Flag | PostgreSQL (today) | Odoo (target) |
| --- | --- | --- |
| `nativeTransactions` | true (one DB) | false across LedgerGuard+Odoo |
| `idempotencyInNativeTransaction` | true | false |
| `supportsCompensation` | false (rollback instead) | maybe later; not required for v0.3 |
| `supportsSimulation` | false | optional; omit if Odoo cannot preview safely |
| `supportsStateVersioning` | weak (re-investigate) | use `write_date` / `__last_update` where available |

Callers **must** branch on capabilities. Never assume PostgreSQL semantics.

## 6. Transaction vs non-transactional semantics

**PostgreSQL:** LedgerGuard DB = SoR. Mutation + key + journal + `VERIFYING`/`RESOLVED` can COMMIT together.

**Odoo:** LedgerGuard DB ≠ Odoo DB. Sequence is:

1. Reserve key in LedgerGuard (visible).
2. Bind fingerprint of Odoo state.
3. Execute constrained Odoo RPC.
4. Re-read Odoo.
5. Verify invariants.
6. Complete key / journal / plan in LedgerGuard.

Crash between 3 and 6 is the **normal** Odoo case. v0.2 recovery (applied / not_applied / ambiguous) is the product, not a workaround.

Do not pretend Odoo `execute_kw` success is COMMIT of LedgerGuard bookkeeping.

Compensation ≠ rollback. If v0.3 adds compensation, it is a new constrained action with its own authorization.

## 7. Recovery model

Reuse v0.2 classification:

- **applied** — Odoo state matches approved postconditions (quantities, move state, no extra duplicate). Not “the original anomaly disappeared.”
- **not_applied** — Odoo still matches the approved pre-state / same repair still proposed.
- **ambiguous** — `RECOVERY_REQUIRED`, no mutation, no guessed complete.

Recovery still runs **before** fresh `APPROVED → EXECUTING` policy.

Odoo `write_date` changes after approval without matching the approved action → `STALE`, require recompile/reapproval.

## 8. Odoo integration boundary

Target **Odoo 17 or 18 Community** (pick one version in implementation and pin it).

Use **supported external APIs**:

- JSON-RPC / XML-RPC `execute_kw` against documented models
- or the Odoo 19 JSON-2 API if that is the pinned version

**In:**

- `stock.quant`, `stock.move`, `stock.move.line`, `product.product`
- inventory adjustment APIs (`action_apply_inventory` / inventory-mode moves — use the method that exists on the pinned version)
- `write_date` for versioning

**Out:**

- Direct SQL against `stock_quant` / `stock_move`
- Bypassing Odoo constraints, company rules, or uom conversion
- Arbitrary `execute_kw` of model/method names from the LLM
- Installing an Odoo “LedgerGuard approval” module as the product

LedgerGuard remains outside Odoo. Odoo is a SoR behind an adapter.

## 9. First Odoo demo scenario

**Narrow flow: duplicate receipt stock move / overstated on-hand quantity.**

Story:

1. Seed (or document) an Odoo product with on-hand 20 from two identical inbound moves of 10 against one receipt.
2. LedgerGuard reads quants + moves (projected snapshot).
3. Deterministic plan: reverse/cancel **only** the duplicate move (or apply a constrained inventory adjustment of −10 bound to that move identity).
4. Policy: `REQUIRE_APPROVAL` above threshold.
5. Human approval bound to plan version + Odoo fingerprint.
6. Adapter validates the action is on the allowlisted method.
7. Execute through Odoo ORM/RPC.
8. Re-read quants.
9. Verify: on-hand = 10, original move untouched, no extra move created.
10. Receipt: `COMMITTED` only if verification PASS.

If Odoo returns success but on-hand is not 10 → `VERIFICATION_FAILED` / `RECOVERY_REQUIRED`, never “verified.”

One action type is enough. Do not add POs, invoices, or payroll.

## 10. Test strategy

- **Contract tests** against an in-memory fake implementing the SDK (capabilities false for native tx).
- **PostgreSQL adapter** continues to pass v0.2 integration tests (regression).
- **Odoo:** dockerized Odoo Community + demo DB in CI, or a documented opt-in job if too heavy for default CI.
- Adversarial:
  - stale `write_date`
  - duplicate RPC retry
  - RPC 200 + failed invariant
  - unauthorized model/method
  - LLM-supplied method name rejected
  - recovery applied / not_applied / ambiguous

Do not weaken v0.2 crash-recovery A–G.

## 11. Security / threat considerations

- Odoo credentials live in the **trusted runtime**, never in model output.
- Allowlist of `(model, method, domain)` — not a generic RPC proxy.
- Company / warehouse / location IDs come from the approved plan, not the LLM.
- Agents still cannot approve.
- Odoo user used by the adapter should be a dedicated integration user with the minimum stock rights.
- Do not store Odoo passwords in git. Demo uses env vars.
- Compromised Odoo admin is out of scope (same class as stolen PG credentials).

## 12. Package layout

Do **not** add empty packages for aesthetics.

**Phase A (SDK):** extend `@ledgerguard/core` ports (`AdapterCapabilities`, snapshot/action types). Keep PostgreSQL as `packages/postgres`.

**Phase B (Odoo):** add `@ledgerguard/odoo` only when there is real RPC code + tests. A separate package is justified because it will depend on HTTP/XML-RPC and Odoo version pins that core must not import.

Avoid `@ledgerguard/adapter-sdk` as a third package unless core’s public surface becomes too mixed. Prefer core ports + odoo package.

App `execute.ts` should depend on the port, not `PostgresExecutionKeyStore` forever. Keys/journal can stay in LedgerGuard Postgres **as the control plane**, even when the SoR is Odoo.

## 13. Proposed public API (draft)

From `@ledgerguard/core` (additive):

- `AdapterCapabilities` (extended)
- `ConstrainedAction` (replaces SQL table/field for non-PG adapters)
- `ProjectedSnapshot` / mapper from Odoo reads
- `classifyStaleReservation` remains; adapters may supply `classifyRecovery`

From `@ledgerguard/odoo` (future):

- `OdooSystemOfRecordAdapter`
- `OdooConnectionConfig` (url, db, user, api key)
- Allowlisted actions: `reverseDuplicateInMove` | `applyQuantAdjustment` (pick one)

## 14. Migration / backwards compatibility

- v0.2 PostgreSQL demo and `pnpm demo` stay.
- Existing `ProposedCorrection` + allowlisted SQL remain valid for the postgres adapter.
- New action types are additive.
- Do not require Odoo to run unit CI.
- Policy/approval/idempotency APIs stay.

## 15. Implementation phases

1. Document and slightly extend core capability flags + action/snapshot types (no Odoo).
2. Refactor `execute.ts` so keys/journal are a control-plane store, not “the SoR.”
3. In-memory SDK fake + contract tests.
4. `@ledgerguard/odoo` with one allowlisted inventory action against docker Odoo.
5. One README scenario: AI proposes → LedgerGuard authorizes → Odoo adapter executes → verify on-hand.
6. Stop. Do not start ERPNext.

## 16. Explicit non-goals

- Odoo chatbot / Copilot
- Odoo MCP server
- Generic approval UI inside Odoo
- ERPNext, Salesforce, or a connector marketplace
- Arbitrary `execute_kw`
- AI-generated policies or SQL
- Dozens of accounting/inventory action types
- Claiming distributed exactly-once between LedgerGuard and Odoo
- Direct database writes to Odoo

---

The first Odoo adapter is successful when a duplicate-quantity invariant is proven against a real Odoo database, and a misleading Odoo RPC success cannot mark LedgerGuard execution `COMMITTED`.
